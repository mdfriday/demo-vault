# 2026 年如何用 Obsidian 搭建数字花园

![Cover](../Assets/digital-garden-cover.png)

> **我想把积累了很久的一部分知识，做成一座别人也能逛进来的数字花园。**

在 Reddit 的 r/ObsidianMD、r/DigitalGardens 里，这句话几乎每隔一段时间就会以不同措辞出现。
大家真正想要的，往往不是再做一个按日期刷的博客，而是一张**能被找到、能顺着点、能慢慢长的知识地图**。

我们一起来看一看， 2026 年，有哪些办法，可以把文件夹发布成数字花园。

## 大家为什么要建 Digital Garden？

综合社区里反复出现的说法，出发点通常不是「我缺一个网站」。需要网站的人会去使用 WordPress 或 Notion 公开页。会认真考虑 Digital Garden 的人，多半已经在 Obsidian（或类似工具）里写了一段时间，手里有一堆**互链过的笔记**，开始问一个更具体的问题： **这些笔记对我有用。有没有一种公开方式，既不像发朋友圈那样浅，也不像写博客那样被迫「每篇都要完整、都要蹭热点」？**

大家想要发布数字花园的动机通常会有下面这几类：

### 1. 不想做 influencer 式博客，只是想公开写作

你是研究生、独立研究者，或只是长期做笔记的人。导师或周围的人不太鼓励「写博客」——不是反对分享，而是讨厌博客被流量劫持后的味道：标题党、更新KPI、人设经营。你也觉得他们说的有道理，但让知识永远锁在硬盘里，肯定不是你想要的。

于是有人在 r/DigitalGardens 里说到：博客和博主这个词已经被 tiresome influencer tropes 占领了；数字花园更像**个人研究方法 / wiki**——自由、可生长，也不必跟着热点转，或者一直努力维持着自己想要在大家心目中的形象。

博客默认读者是「来看最新一篇」；花园默认读者是「从一个入口走进来，顺着链接逛」。前者逼你看重进度，后者可以让你展示结构。对已经用双链思考的人，会更认同第二种公开方式更匹配大脑的工作方式。所以要的不是「更会写 SEO 标题」，而是一种**更诚实的公开写作形态**：页面可以半熟，链接可以慢慢补，首页是地图而不是时间线。

### 2. 私有笔记长到临界点：积累想变成「可被访问的资产」

你玩 Zettelkasten / 第二大脑几个月，笔记从几十涨到几百。某天你在图谱里看到一片自己都觉得漂亮的连接——关于某个专业主题、一套工作方法、一门课的消化笔记。你忽然意识到：这些内容如果只给自己搜，价值只发挥了 1%；如果别人也能逛，它就变成一种**外部资产**，会变得更有意义，价值也更大了。

Reddit 上常见方法是：私有 Zettelkasten 先跑通，规模上来之后再决定「公开一部分」。有人直接把笔记站挂出去，说希望别人也能用到自己的知识。

私有笔记解决的是「我以后找得到」；公开花园解决的是「别人（和未来的合作者）不需要加我好友、不用等我转发，就能自己走进来」。发布，是「积累」变成「可导航资产」的那一步——这一步一旦发生，笔记的价值公式就彻底变了。值得注意的是，大家很少说「我要把整个 vault 都发布出来」。更真实的需是**只发布一部分，能选择性公开**，而不是一股脑全盘上传。

### 3. Learn in public：专业声誉、可点击的思考痕迹

你在公司做技术、产品或研究。简历上的 bullet point 太单薄；你希望有一个地方，能让未来的同事 / 雇主 / 客户看到你**思考的尝试，和思考问题的方式，解决问题的过程**：踩过的坑、写过的教程、整理过的概念图。有人把它叫 learn in public，对应创业圈的 build in public。

在 r/ObsidianMD 关于「用数字花园分享专业知识」的讨论里，理由很具体：建立声誉、networking、整体利于职业；对商业敏感的人，觉得流量起来后变成内容业务或付费服务也不是不可能；绝大部分人更希望的是开放知识，和开源贡献代码一样，贡献自己的一份力量，让世界变得更美好。

LinkedIn 帖子目的太单调，博客又太「营销」。花园介于两者之间：它看起来像一份活的 wiki，带有个人气质。对招聘方或合作方，「逛他的知识站十分钟」往往比「读他的自我介绍」信息密度更高——因为你能看到不同的细节，生动且更加立体。当然也有边界：NDA、真正的 secret sauce、未公开论文，大家会明确说该留私密。公开的是**可复用的硬知识**，不是公司机密。

### 4. 帮具体的人，而不是刷社交媒体

**典型场景 A：** 你做培训 / 教练 / 社群负责人（Reddit 里有社会马戏项目负责人的例子）。你需要把游戏、方法、流程笔记分享给其他教练——他们要的是「能查、能链、能更新」的知识库，不是又一个 Instagram 账号。

**典型场景 B：** 你写了很多 Obsidian 笔记，但讨厌社交媒体的算法节奏。你想公开写作，又不想被推送绑架。Digital Garden 插件教程帖里常出现一句话：这是我找到的、**不用社交媒体也能把写作公开**的最轻松方式之一。

社交媒体优化的是「停留与情绪」；花园优化的是「查找与关联」。当你的读者是同事、学员、同行研究者时，你需要的是后者。链接可以收藏，结构可以生长，更新不必只是为了表演热度。 这类动机特别「工具敏感」：他们要的是低摩擦发布与更新——因为内容本身已经够忙了，不想再让自己扮演一个运营人员。

### 5. 让双链在网页上仍然成立——延续 Obsidian 里已经形成的思维方式


你日常已经这样写：**另见：[[Prompt Engineering]] 与 [[AI Agents]]**。你还会看反向链接，偶尔打开图谱。某一天你想把「AI」或「某门课」那一支文件夹公开，心里默认的成功标准是：读者点 `[[ ]]` 也能跳，而不是落到 404 或 `file://`。

对 Obsidian 用户，花园几乎是双链习惯的**延展**。连线在脑中已经长这样：Wikilinks -> Backlinks -> Knowledge Graph -> Digital Garden。你希望这种思维方式能延续到网页上，而不是被迫改回「每篇独立长文、禁止半熟、禁止漫游」。


**所以：**多数人建花园，是为了让已有知识被连上、被看见、被用上。形态上反感博客表演，规模上从私有积累延展，职业上要可点击的思考痕迹，协作上要帮具体的人，认知上则是要双链在网页上能继续工作。

## 在真正实操创建数字花园时，大家骂得最多的痛点有哪些？

一句话总结：「我想公开一部分互链知识」而不是「我得学习一堆名词和工具」。

### 痛点一：工具链比写作还陡

你打开 Quartz 文档或某支 YouTube 教程，第一次听到 GitHub Actions、`npm ci`、Node 版本。本地 `npx quartz build` 好像成功了，一 push，Actions 报 `EBADENGINE`：文档说要 Node 20/22，runner 却是 18。

论坛上有人标题直接叫 *I am frustrated*：网站是为上传 Obsidian 笔记做的，但我不懂 Git；跟视频做，全是报错，这已经超出我的技术领域。评论区最高频的建议是——换 Digital Garden 插件吧，友好多了。这个建议好像有些帮助，但要重头去学习另一套工具，想想就头大。

### 痛点二：Obsidian 库里都好好的，但网页上是却点了没反应

本地预览时一切正常；上线后，原来的 `[[笔记]]` 变成怪链，图片只剩说明文字，显示的是一张尴尬不已的破图。还有隐藏 Boss：你用了 Obsidian 主题、CSS Snippets、Callout、一堆插件——发布管线只吃「标准 Markdown 语法」，于是「同一座花园」在读者眼里长得歪七扭八。

双链延续可以灵魂——一旦在网页上失败，花园的核心价值就塌了。你拥有的根本不是花园，仅仅只是一次冰冷的导出。

### 痛点三：不想整库上公网

你 vault 里有日记、半成品、客户材料、还没想清楚的观点。你愿意公开的是「AI 学习」或「某项目方法」那一支。官方 Publish 要求的是整库 / 定价不算便宜，大家在社区里呼声更高的方案是「按属性勾选发布」或「按文件夹发布」。

在讨论里反复出现的观点是：**发布 Vault ≠ 发布我的知识。** 大家要的是「一部分资产公开」，而不是「生活全盘直播」。选择性发布不是高级功能，是安全感和可控感的基本要求。

### 痛点四：完美系统焦虑

你本周本该写三页实质笔记，却花在换主题、改模板、重做 MOC、焦虑「这条不够原子」。有人把这种压力写得很生动：结构化 Digital Garden / Zettelkasten 有审美与形式负担，对自我批评强的人，笔记区变成第二个自我攻击现场，自发性写作反而变得充满英雄主义。

于是自然出现「Commonplace Garden」另一种声音：允许无序、链接随手、不维护也没关系——因为维护本身成了痛点。如果数字花园若变成第二个待办系统，它就背叛了「让知识生长」的初衷。

### 痛点五：选型疲劳

你在 Quartz（定制强、偏工程）和 Digital Garden 插件（库内点发布、选择性好）之间横跳三天；再查自定义域名、Vercel、GitHub Pages 私有仓；你还用 iPad 写笔记，一想到 CLI 就头大。首发还没完成，热情早已消耗殆尽。

工具文章永远在对比参数；用户要的是「下周还能更新」的路径。更新摩擦，往往比首发成功率更能决定花园的健康状态。

## 所以，数字花园到底是什么？

**数字花园 = 一组互链的公开笔记，按意义组织，允许慢慢变成熟，并邀请读者漫游。**

| 博客 | 数字花园 |
|------|----------|
| 按日期刷 | 按主题 / 链接逛 |
| 追求成品帖 | 允许「还在生长」的笔记 |
| 首页 = 最新 | 首页 = 地图 / 入口 |
| 孤立也可以 | 孤儿页会显得坏了 |

你在 Obsidian 里已经具备种子：双链、反向链接、图谱、文件夹与 MOC。缺的往往只是最后一公里——**怎么把一个文件夹变成网站，还让链接活着。**

## 2026 年，大家正在走这几条路

不同工具出发点不一样。以「我要一座能逛的花园」这个最终目标来选，而不是按时髦度来选。

### Obsidian Publish

官方托管，读感接近 Obsidian。

**适合：** 接受官方产品边界与定价，想少碰基础设施的人。  
**社区常提的摩擦：** 价格；以及「整库 / 订阅」，如果想「只公开一部分」，需要自己先把内容拆成另一个独立的库。

### Quartz

几乎是 Digital Garden 的参考实现：双链、图谱、搜索都很「花园」。

**适合：** 愿意（或享受）自己管构建与部署、要深度定制的人。  
**社区常提的摩擦：** Git / Node / Actions；非技术用户挫败感极强；图片与 Obsidian 语法兼容要自己踩坑。  
**公允评价：** 能力强、社区活跃度高；很优秀，但不代表适合「我只是想公开一部分笔记」的每一个人。

### Hugo

强大的通用静态站点引擎。

**适合：** 开发者，或本来就要做完整站点的人。  
**社区常提的摩擦：** 它是网站工具，不是 Obsidian 原生花园按钮；不支持双链，需要自己实现。

### Digital Garden 插件 + GitHub / Vercel 等

勾选笔记、点发布——Reddit 上被大量推荐给「不想学 Quartz」的人。

**适合：** 要选择性发布、更新流程尽量留在 Obsidian 里的人。  
**社区常提的摩擦：** 仍依赖 GitHub 等托管；本地一键导出、密码保护、排序与图片等细节会踩坑；和 Quartz 比，定制上限不高。

### MDFriday Publish：把「文件夹 → 数字花园站」留在 Obsidian 里

如果你的真实想法是：**我想公开一部分互链笔记，最好还在 Obsidian 里点一下就成；别逼我先学 Git 和 Node。** 那 MDFriday Publish 就是为你量身定制的方案——支持文件件级别公开、双链，Callout, Backlinks, Search 等基本功能一应俱全。只需要在 Obsidian 里点几下，就能把文件夹变成可逛的花园站。步骤如下：

1. 右键选中文件夹  
2. 点击「Publish to MDFriday」
3. 一键发布, 获取可分享 URL  

构建完全在本地，上传的是由本地笔记生成的网站内容，不会把原始 Vault 上传到云端。专注的是：**分享知识，而不是工程课。**

## 快速对比（按「建花园」这个任务）

| 方案 | 你大概是谁 | 最大爽点               | 最大摩擦             |
|------|------------|--------------------|------------------|
| Obsidian Publish | 想要官方托管体验 | 省心                 | 价格 / 发布边界是否合拍    |

| MDFriday Publish | 想快速把文件夹发成花园 | Obsidian 内预览与发布、可选范围 | 目前只有一个 Quartz 主题 |

## 常见问题

### 我必须公开整个 Vault 吗？

**不必。** 社区共识几乎一边倒：只公开你愿意公开的部分。日记、半成品、敏感材料留本地，恰恰是花园能长期维持的前提。

### 我不会 Git，还能建花园吗？

**能。** 那意味着你应优先选「库内发布」路径，而不是一上来 Quartz + Actions。等你真需要深度定制，再上工具链不迟——很多技术用户也是这么走的：先公开，再升级。

### Quartz 和「库内插件发布」怎么选？

要极致定制、文档站感、自己运维 → Quartz。  
要选择性发布、更新尽量点一下 → 插件式方案（Digital Garden 插件或 MDFriday Publish 这类）。

### 官方 Publish 呢？

仍然是省心选项之一。若价格和发布边界合适，完全不必为了「替代」而替代。不同工具解决不同问题。

### 原始笔记会上传吗？

**不会。** MDFriday Publish 原则是 **Build locally. Publish the result.** 上传构建后的静态文件；源笔记留在本地，绝不上传云端。

### 密码保护呢？

**支持。**社区里常有人问。需求是：分享给小圈子，但不想被搜索引擎整页端走。

## 结语

大家的需求很清晰：

他们已经在 Obsidian 里链接、积累、思考。  
他们想公开的是**一部分互链知识**——因为讨厌博客表演、因为笔记溢出、因为职业与协作需要、因为双链值得延续。  
他们卡住的，往往是 Git、部署、死链、整库压力，以及「完美系统」焦虑——不是缺少热情。

所以 2026 年谈「如何用 Obsidian 搭建数字花园」，我们需要思考的是：

1. 明确你的出发点（公开、连接、被用上）  
2. 再避开已知陷阱（工具链、选择性、验收链接）  
3. 最后选一条帮你扫除工程障碍的发布方式，能让你专注在内容创作，持续更新上  

如果你愿意折腾，Quartz / 自托管依然优秀。  
如果你希望写作和发布都留在 Obsidian 里，MDFriday Publish 希望把最后一公里变回：选文件夹，本地预览，点发布，分享成功。

因为让知识被看见，本来就应该发生在你已经在思考的地方——而不是发生在又一门工程课之后。

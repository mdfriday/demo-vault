## solver

## jobs
`jobs` is made of build tasks, each one an `edge`. From the plural, there should be more than one.

## scheduler
We were just talking about arranging tasks.
That is what this `scheduler` does. When `jobs` is initialized, it starts executing the loop `s.loop`. Then, when there are build tasks related to `edge`, they can be `dispatch`ed out, and the matching `edge` instance finishes the rest.

## bridge
Who breaks the task apart?
`bridge`. When it receives the parse request `llbBridge.Solve`, `bridge` creates a result-proxy instance, `newResultProxy`, so this proxy can finish splitting the remaining build tasks.
At `loadResult`, it loads the `vertex edge`. This is another key point.
Remember that earlier the `client` read `llb.definition`. Here what replaces it is already `vertex`. That means the conversion is done.
Then the build starts for real. The argument passed in is `edge`. The task is added to `jobs`, arranged by `scheduler`, and finally `edge` builds the `op` through the cache strategy `shareOp.CacheMap`.

## The problem it solves
The next generation of the `docker build` command-line tool.
Because the current tool can only build one file at a time, and they are all `Dockerfile`s. Many projects have more than one build file. Some have several build files, and they depend on each other. The current tool cannot meet those needs.
There is another point: it is slow. Because everything runs in sequence. If it is a large project, such as microservices, the time it takes cannot be endured.

The new generation of the tool is exactly meant to solve these problems.
By building in parallel, it lets the user freely define a frontend description language, parse it into a unified standard operation set, and build projects with these complicated needs. It can also build several projects at the same time.

## Architecture goals
One of the main goals is to separate the frontend of the build from the backend.
The frontend means the user's definition of the build steps.
The backend means building the common operation set in the most efficient way (low-level description of the build operations).

Not an arbitrary task runner.
A long-running service, used to solve the problem of building source into artifacts, and in a way that is independent, portable, repeatable, and the most efficient.

## Important modules
Eight modules in all.

### sources
The resource module, used to fetch data from the remote.
Such as `From ubuntu:14.04`, fetching the base image.

### frontends
Get the build information the user has defined, like the `./example | buildctl build` command Long Fei mentioned.
Used to convert it into the unified backend standard build operation set.
What has to be emphasized is that `Dockerfile` is one form of frontend that is supported. That means everyone can define their own frontend language, their own `Container building DSL`.

Yuan Xiaobai's mouth fell open. Thinking about it, he was a little excited.

### solver
Find the most efficient build strategy, and build the build graph. What is said here is exactly the DAG (directed acyclic graph) Long Fei pointed at earlier. Through all the information the graph carries, including `Operation` and the dependency between operations, it provides data for finding an efficient method later.
Finally it can also cache every operation result, and provide a cache service for later build tasks.
That is powerful. Think about it. Later, people all over the world will not have to build the same thing again and waste compute. That really is a green feat!
The underlying logic of this, I guess, is `content addressable`. It means hashing a file and producing a unique identifier. If a new file is copied from this file, the same HASH algorithm gets the same KEY, and you do not have to build it yourself again. Yes, in theory it works.

### worker
The real component that runs the container.
Such as running a container with `OCI runc`.

### exporter
Export the build result according to the export config, such as exporting a tar package, or a zip package.

### snapshots
Provide filesystem services for build operations, such as on the root filesystem `rootfs`.
This involves LXC (linux container) technology.

### cache manager
The recent build output, and the intermediate results, can all be cached, so a build again has an efficient guarantee.
Here it does not only cache relational data. It can also cache blob data.

### controlAPI
Used to associate several build tasks.
The ones before can more or less be matched to what Long Fei said. This one does not seem to have a matching flow. Maybe it is not in the main sequence diagram.

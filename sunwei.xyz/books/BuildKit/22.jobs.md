Worker is used to actually run the container. What is the positioning of jobs?

With that question, Yuan Xiaobai opened `j.list.load(e.Vertex, nil, j)`. A little earlier he had seen that when Job is initialized, j.list refers to the Solver in jobs.go, so j.list.load is:
```golang
func (jl *Solver) load(v, parent Vertex, j *Job) (Vertex, error) {
   jl.mu.Lock()
   defer jl.mu.Unlock()

   cache := map[Vertex]Vertex{}

   return jl.loadUnlocked(v, parent, j, cache)
}
```
The arguments passed in, v and parent, are both Vertex. Among them v is edge.Vertex. From the function definition, a vertex is passed in, and a vertex is also returned. It looks like it did some processing on the vertex. What the code actually calls is jl.loadUnlocked:
```golang
func (jl *Solver) loadUnlocked(v, parent Vertex, j *Job, cache map[Vertex]Vertex) (Vertex, error) {
   if v, ok := cache[v]; ok {
      return v, nil
   }
   
   ...
}
```
It takes the vertex directly from the Cache map that was passed in. If it is there, it returns directly. Then we can see the cache here refers to the Vertex in the Edge that is being processed.
```golang
func (jl *Solver) loadUnlocked(v, parent Vertex, j *Job, cache map[Vertex]Vertex) (Vertex, error) {
   ...

   inputs := make([]Edge, len(v.Inputs()))
   for i, e := range v.Inputs() {
      v, err := jl.loadUnlocked(e.Vertex, parent, j, cache)
      if err != nil {
         return nil, err
      }
      inputs[i] = Edge{Index: e.Index, Vertex: v}
   }
   ...
}
```
Recursion appears here again. And it loops, according to the vertex's input, loading the vertex that is in the unlocked state. What is worth noting is that the parent used here is the same one. It is not the Vertex of the level above.
You can see each level only cares about the input of its own level.
```golang
func (jl *Solver) loadUnlocked(v, parent Vertex, j *Job, cache map[Vertex]Vertex) (Vertex, error) {

   // if same vertex is already loaded without cache just use that

```
The focus here is converting vertex into vertexWithCacheOptions, that is, a state suitable for the cache.
Right after that, state is created. This state, from the struct's data items, combines all the job-related information.

Overall, it converts every vertex into a state that has cacheOptions, and associates the matching state with dgst (the unique identifier of the vertex).

Then look at Build:
```golang
func (j *Job) Build(ctx context.Context, e Edge) (CachedResult, BuildInfo, error) {
   ...
   v, err := j.list.load(e.Vertex, nil, j)
   ...
   e.Vertex = v

   res, err := j.list.s.build(ctx, e)
   ...
   return res, j.walkBuildInfo(ctx, e, make(BuildInfo)), nil
}
```
After converting the vertex into a vertex that has the cacheOptions state, it replaces the original Vertex: `e.Vertex = v`.
Finally it builds with j.list.s.build.

`j.list.s` refers to the scheduler. It seems every job has its own scheduler, and this scheduler needs a vertex that has cache information in order to build.

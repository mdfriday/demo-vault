## A pipe use: Receive
```golang
func TestPipe(t *testing.T) {
   t.Parallel()

   runCh := make(chan struct{})
   f := func(ctx context.Context) (interface{}, error) {
      select {
      case <-ctx.Done():
         return nil, ctx.Err()
      case <-runCh:
         return "res0", nil
      }
   }

   waitSignal := make(chan struct{}, 10)
   signalled := 0
   signal := func() {
      signalled++
      waitSignal <- struct{}{}
   }

   p, start := NewWithFunction(f)
   p.OnSendCompletion = signal
   go start()
   require.Equal(t, false, p.Receiver.Receive())

   st := p.Receiver.Status()
   require.Equal(t, st.Completed, false)
   require.Equal(t, st.Canceled, false)
   require.Nil(t, st.Value)
   require.Equal(t, signalled, 0)

   close(runCh)
   <-waitSignal

   p.Receiver.Receive()
   st = p.Receiver.Status()
   require.Equal(t, st.Completed, true)
   require.Equal(t, st.Canceled, false)
   require.NoError(t, st.Err)
   require.Equal(t, st.Value.(string), "res0")
}
```
You can see that if I want to execute a blocking function through pipe, such as:
```golang
f := func(ctx context.Context) (interface{}, error) {
   select {
   case <-ctx.Done():
      return nil, ctx.Err()
   case <-runCh:
      return "res0", nil
   }
}
```
This scene is very common. For example an HTTP network request has to wait until runCh receives a message before it can return a result.
While we use `NewWithFunction` to create the pipe, it also returns a start function. At the same time we can set the pipe's OnSendCompletion event. That way, when the send action finishes, we can do what we want to do. What we want to do here is signal: add one to the counter signalled, then write information into the waitSignal channel.
It can be understood as: when the send operation finishes, notify through the waitSignal channel.

The pipe executes `go start()`. The basic Goroutine unit is created.
At this time, when you check the Status of the pipe's Receiver, you find it has not really executed:
```golang
require.Equal(t, false, p.Receiver.Receive())

st := p.Receiver.Status()
require.Equal(t, st.Completed, false)
require.Equal(t, st.Canceled, false)
require.Nil(t, st.Value)
require.Equal(t, signalled, 0)
```
Closing the runCh channel triggers the return of the user function's final result.
But at this time you still have to wait for the Goroutine `go start()` to really run. Wait with <-waitSignal.
When the pipe's OnSendCompletion is called, that means the message of the waitSignal channel has been received, and execution can continue.
Then look at the matching state. The change we expected has happened:
```golang
p.Receiver.Receive()
st = p.Receiver.Status()
require.Equal(t, st.Completed, true)
require.Equal(t, st.Canceled, false)
require.NoError(t, st.Err)
require.Equal(t, st.Value.(string), "res0")
```

## A pipe use: Cancel
Different from Receiver working normally, Cancel cancels the request:
```golang
p.Receiver.Cancel()
<-waitSignal
```
The result we expect: the request is really canceled:
```golang
p.Receiver.Receive()
st = p.Receiver.Status()
require.Equal(t, st.Completed, true)
require.Equal(t, st.Canceled, true)
require.Error(t, st.Err)
require.Equal(t, st.Err, context.Canceled)
```

Through the use scenes of the pipe, we can understand the original design intention.
The hope is that, like a pipe on Linux, a request is put in at one end, and the result is received at the other end.
The request here can be a function, f, and it can be an asynchronous operation. When the request is really sent, we have a callback function, so the user can continue handling or trigger a further operation.
Finally, through the Receiver's state, receive the return state and the return result. This result is the result the user really requested.

Then imagine: what if several pipes are connected together?
For example there are three pipes in all, connected to each other. When the result managed by the previous one wants to be passed to the next one, the next manager can hold the previous pipe's Receiver, and register a trigger event in the previous pipe's OnSendCompletion event. Then, can the dependency order be set, and executed according to the plan?!
